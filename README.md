# agent-symphony

> 多 Agent 编排的**理论 + 实操**资料包。
> 一份讲**为什么这么设计**，一份讲**具体怎么敲**。
>
> 实操部分来自一个真实跑通的多 Agent 工程项目，不是纸上设计 ——
> 里面的判据、坑、模板都是踩过之后写下来的。

---

## 1. 这是什么

一套**可落地的多 Agent 协作方案**，围绕 Herdr（终端 agent 编排器）展开，包含：

| 内容 | 形态 | 能直接用吗 |
|---|---|---|
| **体系化学习路线** | 5 个阶段、18 章，含前置知识、验收问题与项目参照 | 按顺序学习，配合实操验证 |
| **章节正文** | 五类目录、18 章 + 术语、来源、案例与逐项索引 | 按理论导航阅读和实践 |
| **原理论大纲** | 历史专题问题清单 | 全部编号小节已关联正文 |
| **通用 skill** | 完整编排协议 + 3 份参考 + 3 个工具 | **能**，复制到项目即可 |
| **Claude skill** | Claude Code 覆盖层 | **能**，配合通用版使用 |

### 它不是

- ❌ 不是某个开源编排框架的复刻。仓库名叫 `agent-symphony`，但内容是一套**自研的实践协议**，
  与同名的其他项目无继承关系。
- ❌ 不是「装好就能自动跑」的成品。它要求你已经有一个能起多个 agent 的终端环境。
- ❌ 不是模型评测或 prompt 大全。它只关心**怎么组织多个 agent 把一件事做完**。

---

## 2. 解决什么问题

单 Agent 干复杂任务会撞上四个天花板：

1. **上下文溢出** —— 读不完所有相关文件
2. **注意力稀释** —— 任务一多就丢细节
3. **单点阻塞** —— 一个环节卡住，全线停摆
4. **无法自证** —— 自己写的自己验，盲点相同

多 Agent 能解决这些，但会引入新问题：**协调成本、返工、假验证、上下文丢失**。
这套协议就是针对这些问题的答案 —— 每一条规则背后都有一次实际踩坑。

## 3. 快速开始

### 3.1 前置条件

```bash
# 必须在 Herdr 里，否则不要执行 herdr 命令
test "${HERDR_ENV:-}" = 1 || echo "不在 Herdr 里"
```

还需要：至少两个不同 kind 的 coding agent（如 Claude Code + Codex）。

### 3.2 装 skill

```bash
# 通用版：Agent Skills 标准位置
cp -r 02-实操/skill-通用 .agents/skills/herdr-orchestration

# Claude Code 额外一步：它不扫 .agents/skills，需要 junction
powershell -NoProfile -Command "New-Item -ItemType Junction `
  -Path '.claude\skills\herdr-orchestration' `
  -Target '.agents\skills\herdr-orchestration'"
```

⚠️ junction 会被 git 当成第二份文件 —— 记得 `.gitignore` 挡住。详见 `02-实操/README.md` §3。

### 3.3 跑第一个任务

1. **判档** —— T0（派 1 个 worker）/ 组级（派小组）/ T1（Claude 策划）/ T2（Codex 策划）
2. **派活** —— 起 agent 带免审批参数，起完**验模型**
3. **委托** —— 目标 / 验收标准 / 边界 / 回报要求，四件事写全
4. **验证** —— 验证者必须与作者**不同 kind**
5. **收尾** —— **保留 agent 和工作区**，别关

## 4. 核心设计（四条）

| 原则 | 为什么 |
|---|---|
| **secretary 只派活、不干活** | 保持空闲，才接得住新需求、才随时能汇报 |
| **按能力档位分派，不用满所有人** | 稀缺模型做判断，普通模型做执行 |
| **验证者与作者不同源** | 换 kind 就换了实现和工具链，能覆盖大部分盲点 |
| **任务收口 ≠ 关闭 agent** | 活着的 agent 握着上下文，用户追问一句就够；关了要重读重推导 |

学习入口见 [理论导航](01-理论/README.md)，依次阅读基础、协作、恢复、治理和评估；十八章正文已按学习顺序展开，可执行细节在 `02-实操/`。

## 6. 两份 skill 的关系（**不是两份拷贝**）

```
         skill-通用/                ← 唯一真源：协议主体
              ↑ 引用章节号
         skill-claude/              ← 薄覆盖：只写 Claude 特有的差异
```

- **通用版**：角色模型、分级判据、命名规范、herdr 用法、委托模板。
  Claude Code / Codex / OpenCode 都能读。
- **Claude 版**：只写 Claude Code 才有的东西 ——
  模型槽位（`--model fable` 才是最强档）、MCP 清单、skill 发现要用 junction、专属坑。

> 做两份完整拷贝必然漂移：改一边忘一边，最后没人知道哪份是对的。
> 所以一个当主体，一个当补丁 —— **改协议先改通用版**，再回看 Claude 版有没有失效。

## 8. 适用前提与局限

**前提**

- 有一个能同时跑多个 coding agent 的终端（本包按 Herdr 写）
- agent 之间能通过文件系统共享工作目录
- 你愿意接受「先派活、不亲自干」的工作方式

**局限 —— 用之前请先读**

- ⚠️ **强绑定 Herdr**。协议本身（角色 / 分级 / 分派 / 验证）是通用的，
  但所有命令、窗格、命名都围绕 Herdr 的实现。换编排器要重写 §5 全章。
- ⚠️ **强绑定本机模型配置**。`reference/agent-profiles.md` 里的槽位映射是
  **某一台机器某一时刻**的实测值。换机器必须重跑文末的复验命令。
- ⚠️ **可派活的 agent 只有三个**：`claude` / `codex` / `opencode`。
  别照着旧版本档案把其他 kind 加回来。
- ⚠️ **工具脚本的状态行解析器按各家 TUI 写的**，改版可能失效；
  失效表现是「模型列显示未知」而不是报错 —— 别把它当强校验。

## 10. 维护规则

1. **协议改在通用版**，Claude 版只补差异 —— 别在两边各写一套。
2. **理论部分不写具体命令**，命令只存在于实操部分。否则同一个操作会有两个版本。
3. **改了工具就重跑 `--selftest`**，别让脚本悄悄失效。
4. 新增 agent kind 时，同步三处：`SKILL.md` §2.1 能力表、`agent-profiles.md` §2 派活矩阵、
   `herdr-audit.py` 的 `KINDS` 集合。
