# 交接模板（直接抄，别自由发挥）

> 配套 `../SKILL.md`。四个环节各一个模板。**照抄比自创好** —— 字段固定了，
> planner 才能机械校验、verifier 才能逐条对账、事后才查得清。

---

## 1. main → planner（委托）

```
【任务】<一句话说清要达成什么，可判定>

【验收标准】
1. <可判定的标准，例如"脚本跑完 exit 0 且输出包含 X">
2. <...>

【边界】
- 不许碰：<路径 / 表 / 系统 / 分支>
- 生产：<无 / 有，见下方授权>
- 根仓 E:\XY 永不推远程（固定）

【回报要求】
- 完成后给：做了哪些子任务 / 各自结论 / 哪些没做及原因
- 有生产操作时，必须带 [PROD-OK]

【生产授权】          ← 没有就整段删掉
[PROD-OK] env=<环境> action=<动作> target=<对象> at=<时间> by=main
```

---

## 2. planner → worker（任务书）

> ⚠️ **worker 是全新进程**：没上下文、没读这份 skill。**下面每一格都必须填**。

```
【角色】你是 <task>-<scope>，只负责 <范围>。范围外的东西一律不碰。

【背景】<为什么做，1–3 句；涉及的路径写全>

【要做的事】
1. <具体动作，可执行。不要写"优化一下">
2. <...>

【验收标准】
1. <可判定：跑什么命令、看什么输出、比对什么数字>

【边界】
- 只改：<文件/目录清单>
- 不许碰：<文件/目录/表/系统>
- 根仓 E:\XY 永不推远程
- 不确定就停下来回报，不要自己决定

【生产授权】          ← 非生产任务整段删掉
[PROD-OK] env=<...> action=<...> target=<...> at=<...> by=main

【产出】<改哪些文件 / 报告写到哪个路径>

【回报格式】
① 改了什么（文件:行）
② 怎么自证的（命令 + 实际输出）
③ 没做的和原因
```

---

## 3. verifier 领取验证任务（planner → verifier）

```
【角色】你是 <task>-validation。你**不是**作者，你的活是挑错，不是确认它对。

【背景】<谁做了什么，产物在哪>

【验收标准】（原样抄 worker 的，不要改写）
1. <标准>

【你要做的】
1. 逐条判定上面的标准：通过 / 不通过
2. 每条都要有证据：命令、输出、文件:行
3. 不要修任何东西

【边界】
- 只读。**不许修改产物**
- 不确定就标"无法判定"并说明缺什么

【产出格式】
| # | 验收标准 | 结论 | 证据 |
|---|---|---|---|
| 1 | <原文> | 通过 / 不通过 / 无法判定 | <命令或输出或 文件:行> |

【总体结论】<可交付 / 不可交付，一句话理由>
【发现但不在标准内的问题】<有就列，没有写"无">
```

---

## 4. planner → main（汇总回报）

```
【任务】<原来那句目标>
【结论】<可交付 / 部分可交付 / 不可交付>

【已验证通过的】
- <子任务>：<结论一句> —— 验证者 <task>-validation，证据：<命令/文件:行>

【验证不通过的】
- <子任务>：卡在 <哪一条> —— 已 <修过一次并重验 / 未修，原因>

【没做的】
- <子任务>：为什么没派（没有合适 agent / 缺授权 / 缺信息）

【生产操作】（有才写）
- <动作> —— [PROD-OK] by=main at=<时间>

【需要你或用户决定的】
- <一句话一个问题>
```

> ⚠️ **三段必须分开。** 把"没做/没验"混进"已完成"里，等于骗人。
> main 转述给用户时**也必须保留这个区分**。
