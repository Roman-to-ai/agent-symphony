# 07 · 通信协议与向上汇报

> 前置：04—06。目标：让消息支持决策，避免下达后无人知道任务发生了什么。

## 1. 分开传输与业务协议

终端输入注入、文件、RPC、队列都是传输方式；“接收”“阻塞”“交付”是业务含义。同一条消息通过不同通道发送，业务语义应保持一致。终端回到输入提示符只代表一次交互结束，不自动代表任务成功。

本项目通过主动推送与主动读取形成回报链。这能缓解无人查看下级窗口的问题，但不是具备持久化确认、去重和重放能力的消息系统。

## 2. 消息身份与最小字段

建议消息包含 message_id、task_id、attempt_id、task_version、sender、type、payload 和 evidence_refs。时戳用于诊断，不宜单独决定全局顺序；任务版本和服务端状态校验更适合拒绝过期更新。

| 类型 | 何时发送 | 接收后的处理 |
| --- | --- | --- |
| accepted | 理解任务后 | 确认已接收，记录开始预期 |
| progress | 里程碑或约定周期 | 更新进展，必要时调整依赖 |
| blocked | 无法自行消除障碍 | 指定解除者和下一步 |
| heartbeat | 按存活策略 | 更新租约或健康记录 |
| submitted | 产物可检查 | 进入待验收状态 |
| failed/cancelled | 无法继续或停止完成 | 决定恢复、补偿或关闭 |

## 3. 向上汇报应包含什么

进展报告应给出已完成事实、证据、剩余工作、阻塞和所需决策。百分比只有在分母明确时才有意义；“完成 80%”不如“接口和后端通过，前端回跳及集成未验”。

汇总时分别保留已验证、未通过或未验证、未执行三类。上级可以压缩描述，但不能把不确定内容升级为确定结论。摘要引用原始报告，保证跨层追溯。

汇报频率按任务风险和阶段变化决定。频繁汇报会占用执行与管理预算；稀疏汇报会延长异常发现时间。里程碑与异常触发通常值得保留，长任务再补周期检查。

## 4. 丢失、重复、乱序与取消

发送端在未收到持久确认时可以重发同一消息 ID；接收端应根据 ID 去重，并校验任务版本、尝试身份和合法状态转换。先收到结果后收到旧进展，不应把任务退回执行中。

发送成功、传输接收、业务处理完成是不同确认层次。是否需要全部实现取决于可靠性要求。取消消息到达前已发生的外部操作仍可能完成，因此还需查询效果和补偿。

## 5. 示例与验收

后端 Worker 汇报“测试环境不可达，补丁已生成，本地用例通过，需要环境负责人恢复服务”。上级据此把任务标为待外部验证，并可安排不依赖环境的代码审核；不能仅把状态写成失败后盲目重启。

**练习：**按结果、旧进展、重复结果、取消的顺序输入消息，写出每步允许的状态变化与拒绝原因。
