## 阅读现有协议时需要区分的边界

- secretary、planner、group、worker、verifier 是本项目的角色设计；一般理论允许根据任务合并或拆分职责，不要求所有任务经过全部角色。
- 理论中的 Worker 是广义执行单元；现有协议中的 worker 通常特指末端执行角色。阅读时按上下文区分。
- “不同 kind 验证”是本项目降低共同盲点的实践规则。不同客户端或模型仍可能共享错误，需要证据、测试和整体验收支撑。
- “保留 Agent”有助于延续当前上下文，但不等于持久化检查点；进程或主机失效后的恢复需要另行设计。
- 窗格、命名和 TUI 状态用于观测运行环境；它们不能单独证明业务任务正在推进或已经完成。
- 原大纲第 4 章的输入注入与输出读取描述适用于本项目的终端协作场景。其他系统也可能使用消息队列、共享状态或 RPC 等通信方式。
- 学习路线引用的公开项目用于理解机制，不构成框架迁移或运行协议变更。

## 建议先补齐的工程闭环

先用一个小任务验证：任务契约 → 分工 → 主动汇报 → 产物与证据 → 独立验收。

随后补充：持久任务状态 → 中断接手 → 重复操作处理 → 旧执行者隔离 → 预算与并发控制 → 基线对照实验。

每一步记录实际证据；缺少运行验证的内容继续标注为设计或待补，避免把理论目标当成当前能力。
