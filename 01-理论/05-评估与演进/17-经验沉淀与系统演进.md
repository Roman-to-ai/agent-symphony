# 17 · 经验沉淀与系统演进

> 前置：09、12、16。目标：把有效经验转化为可维护规则，并控制错误传播。

## 1. 经验从哪里来

失败日志提供症状，复盘提供可能原因，对照和复验才帮助判断改进是否有效。一次任务成功可能来自任务简单、环境偶然或额外人工介入，不能立即固化为普遍策略。

经验条目应记录问题、适用条件、方法、证据、反例、来源、版本和复验日期。例如“接口不稳定时先冻结契约”比“永远先做后端”更能表达适用边界。

## 2. 经验写入哪一层

| 层次 | 适合保存 | 不宜混入 |
| --- | --- | --- |
| 当前任务记录 | 临时假设、排查路线和进度 | 未验证的全局规则 |
| Skill | 可复用流程与检查方法 | 瞬时凭证或机器私有状态 |
| 能力档案 | 模型、工具、环境的验证结果 | 无证据的永久排名 |
| 编排政策 | 调度、预算、授权与验收规则 | 单次任务的特例 |

提炼时保留具体证据，但删除敏感内容和过度特定的偶然条件。

## 3. 版本与发布过程

建议流程是提出变更、说明动机、选择验证集、与基线比较、小范围采用、观察并回滚。提示词、Skill、工具、模型配置和任务协议都需要能识别版本。

变更输出格式或状态字段时，还需考虑运行中的旧任务。可以兼容旧版本、固定旧任务配置，或显式迁移；不能直接修改文件后假定所有实例同时理解新协议。

## 4. 项目维护中的一致性

本仓库通用 Skill 是协议主体，Claude 覆盖层补差异。修改主体后检查覆盖层、模板、能力档案和工具假设，避免两套规则漂移。理论描述通用机制，实操文档承载具体命令。

新增 Agent kind 时应同步协议、能力矩阵和审计工具；先确认实际能力再加入阵容。修改工具后执行适用自检，文档变更则重点验证链接、引用、章节和行为说明。

个人工具变为团队规范时，还需要明确维护责任、变更审批范围、问题反馈方式和成员培训。规范价值在于减少协作歧义，不能仅以规则数量衡量成熟度。

## 5. 自动优化的边界

历史成功率可以帮助路由，但需要考虑任务难度和样本量；高成功率可能只是一直分到简单任务。在线探索需要预算、保护范围和回退策略。

动态组织和策略学习应在可靠评估之后引入。若奖励只看完成速度，系统可能少做验证；若只看人工介入率，可能隐瞒阻塞。目标函数必须包含质量和约束。

## 6. 练习与验收

选择一条当前协议，写明问题、机制、适用条件和反例；设计一个能够否定它的实验。再模拟更新后质量下降，说明如何定位版本、撤回规则和处理在途任务。
