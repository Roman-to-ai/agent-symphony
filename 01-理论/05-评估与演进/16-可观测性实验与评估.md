# 16 · 可观测性、实验与评估

> 前置：01—12；基础记录从第一次实践就开始。目标：知道系统为何成功或失败，用对照而非印象优化。

## 1. 建立可追溯链

目标、契约、任务、尝试、Worker、模型调用、工具动作、产物和验收之间应能通过 ID 关联。单独保存终端截图便于现场观察，但不利于跨尝试统计和恢复。

一次执行记录至少包含时间、任务和尝试身份、模型配置、动作类别、结果、耗时、消耗和证据引用。记录外部可观察事实和决策摘要，不要求保存内部思考过程，也不应泄露凭证。

## 2. 指标与分母

| 指标 | 建议定义 | 常见误用 |
| --- | --- | --- |
| 端到端成功率 | 满足整体验收的任务数／纳入评估任务数 | 排除失败或超时任务 |
| 交付耗时 | 接收目标到整体验收 | 只计模型生成时间 |
| 单次交付成本 | 所有尝试和协调成本／交付数 | 忽略失败尝试 |
| 返工率 | 需要返工的提交／受验提交 | 把需求变化全部算执行错误 |
| 协调开销 | 组织、交接、等待等消耗 | 与业务执行重复计费 |
| 恢复时间 | 故障发生或检测到恢复的约定区间 | 不说明起止点 |

质量不能总压缩成一个数。对代码、研究、数据任务可以分别保留正确性、覆盖、证据和约束遵循维度。

## 3. 基线与对照设计

先建立单 Agent 基线，再比较多 Agent。保持任务集合、工具权限、验收标准和预算可比；若同时更换模型和组织结构，应说明无法单独归因组织收益。

准备常规、边界、失败和高耦合任务，事先定义成功标准。多次运行并报告分布或范围，记录超时与失败。小样本结果只能说明初步趋势，不能据此宣称普遍更优。

消融实验可以依次去掉组长、独立审核或周期汇报，观察质量与成本变化。每次尽量改变一个机制，便于理解真正作用。

## 4. 故障注入和事故复盘

故障注入应有目标、环境、触发点、预期行为、实际证据和恢复结果。例如“工具成功后丢响应”检验幂等，“协调者重启”检验状态接管。

事故复盘分开事实时间线、直接原因、系统条件、改进方案和复验结果。没有实际证据时写成假设或演练设计，不能编造“本轮事故”。

本项目状态表和审计脚本有助于观察名称、容量与模型显示；TUI 解析失败时，“未知”不等于模型实际错误，也不能作为强校验。[实操导航](../../02-实操/README.md)

## 5. 练习与验收

取一组固定任务，比较单 Worker、协调者加并行 Worker 两种设计，记录质量、总成本、等待和返工。写出一个你原先相信、但数据没有支持的判断，并说明下一次实验如何区分原因。
