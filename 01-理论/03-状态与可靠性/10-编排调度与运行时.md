# 10 · 编排、调度与运行时

> 前置：05—09。目标：把语义判断与可靠执行职责分开。

## 1. 谁负责哪类决定

| 组件 | 输入 | 输出 | 应保持的约束 |
| --- | --- | --- | --- |
| 规划者 | 目标、证据、约束 | 任务图和修订建议 | 不隐式扩大授权 |
| 编排器 | 任务图、事件、状态 | 合法状态转换 | 依赖和版本一致 |
| 调度器 | 就绪任务、资源、配额 | 分配与启动决定 | 不超并发和预算 |
| 运行时 | 分配、能力配置 | 实例执行和事件 | 身份、环境、取消可追踪 |
| 控制器 | 期望状态、实际状态 | 修复或调整动作 | 不争抢他人所有权 |

小系统可以把这些放在一个进程里，职责仍应分清。否则一次“模型建议重试”可能绕过预算和重复操作检查。

## 2. 事件驱动的状态推进

以任务 submitted 为例：先验证消息身份与版本，保存产物引用，再把任务转为待验收，最后触发验收任务。验收通过后才释放依赖它的后续任务。

重复处理同一事件应有一致效果。对“保存状态后发送消息”的跨系统步骤，可以使用持久待发送记录并重试投递；接收端仍需去重。只把数据库和消息发送放在相邻代码行，不会自动获得原子性。

## 3. 期望状态与控制循环

期望状态描述希望保持的事实，例如“任务 A 有一个有效执行者”“预算超限后没有新的模型请求”。控制循环读取实际状态，发现偏差，执行修复，再观察结果。

Kubernetes 控制器采用持续使实际状态接近期望状态的方式，适合借鉴这种纠偏思想。[Controllers](https://kubernetes.io/docs/concepts/architecture/controller/)

Agent 结果正确性不能仅靠副本数量保证。控制器可以维持实例，但语义质量还需要任务验收和评估。不同控制器也应有清晰所有权，防止一个扩容、另一个立即回收而持续振荡。

## 4. 从手工协议演进

第一步把计划与任务书落文件；第二步统一任务 ID 和状态；第三步把接收、提交、验收事件结构化；第四步加入持久状态、恢复和调度规则。这样可以逐步自动化，而不必一开始复制完整分布式平台。

本项目已有手工角色分工、任务文件和 TUI 辅助观测，尚不能据此断言具备完整事件存储或自动恢复。AutoGen 的 runtime 概念有助于理解执行与消息管理的职责边界。[Agent 与多 Agent 应用](https://microsoft.github.io/autogen/stable/user-guide/core-user-guide/core-concepts/agent-and-multi-agent-application.html)

## 5. 练习与验收

为登录任务写出 waiting、ready、running、blocked、submitted、accepted、failed、cancelled 的转换表，标明触发者和校验条件。再测试重复提交、先取消后提交、旧实例回报三种情况。

通过标准：不合法事件不能推进状态；丢失一个进程后，权威记录仍能说明发生了什么。
