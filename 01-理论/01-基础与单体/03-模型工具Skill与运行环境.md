# 03 · 模型、工具、Skill 与运行环境

> 前置：01—02。目标：建立能力画像，能够定位失败发生在哪一层。

## 1. 能力是组合条件

同一个客户端换模型，推理表现可能改变；同一个模型接入不同工具，可执行范围也不同。Worker 能力应拆成模型、策略、工具、知识、上下文、权限、环境和预算。缺少必要条件时，其他维度再强也无法完成任务。

能力画像应保存实际模型身份、任务类型上的验证结果、工具及版本、可访问范围、上下文限制、成本与时延。客户端显示的槽位名称不一定是实际模型，部署时需要按环境确认。

## 2. 模型选择与能力验证

先列硬条件，例如必须理解截图或能够输出工具参数；再在满足硬条件的候选中比较任务质量、成本和响应时间。不要仅依据模型名称、排行榜或默认档位分配职责。

对重复业务，可以准备小型代表任务：一例常规、一例边界、一例工具异常。画像记录证据与日期，配置变化后重新验证。不要把某次客户端网络失败直接解释为模型推理较弱。

## 3. 工具与 Skill 的分工

工具负责动作，Skill 提供方法。例如工具可以查询数据库，Skill 规定先确认口径、再取样、最后对账。方法无法创造不存在的权限；工具可用也不意味着 Agent 知道如何正确使用。

工具契约需要说明输入、返回值、超时、错误、是否写入以及重复执行的后果。返回“请求成功”可能仅表示接收成功，业务完成还需查询状态。工具异常应区分输入错误、临时失败、权限不足和永久不可用。

MCP 的架构包含 host、client 和 server，用来连接工具、资源等能力。它不保证工具返回正确，也不替代任务授权和业务验收。[MCP 架构](https://modelcontextprotocol.io/docs/learn/architecture)

## 4. 多模态与运行环境

识别图片先检查输入质量、分辨率、裁剪范围和所需细节。看懂页面不等于能操作页面；操作还依赖浏览器、坐标或元素定位工具。对图表中的精确数字，应优先读取原始数据或通过专门工具验证。

运行环境应声明工作目录、依赖、网络、系统工具和文件权限。一个可复现环境需要固定重要版本并保留必要配置引用，凭证通过受控方式注入，不能写入共享交接文档。

## 5. 示例与故障定位

Worker 无法完成截图对账：先判断是否能读取图片，再判断数字是否清晰，接着确认是否能取得源表，最后验证口径。若源表权限缺失，换更强模型未必有用；若图片信息不足，继续放大推理预算也不能补出缺失数据。

**项目对应：**[能力档案](../../02-实操/skill-通用/reference/agent-profiles.md) 是本机能力记录；其中槽位和工具配置应复验，不作为长期不变事实。

## 6. 练习与验收

为一个 Worker 填写硬条件、可选能力、环境、授权、成本和验证日期。拿一个失败案例，指出缺失条件，并设计只改变一个变量的复验。
