# 01 · 基本概念与系统边界

> 前置：无。目标：能够拆解一个 Agent 系统，而不把模型、客户端和运行实例混为一谈。

## 1. 从一次任务理解系统

本文适合希望设计、维护或评估 Agent 协作系统的读者；只需要调用单次模型接口时，可以先掌握基础与任务契约，无须立即建设多 Agent 平台。理论解释为什么和如何取舍；具体操作命令、机器配置与软件参数继续以实操目录为准。

用户要求“修复登录失败”，系统需要读取需求、检查代码、选择行动、运行工具、验证结果并汇报。模型生成下一步建议，Agent 执行逻辑决定如何使用建议，工具操作环境，运行实例承载整个过程。多个实例之间的依赖、授权和恢复由编排系统协调。

模型本身不必拥有文件权限；客户端能访问文件，也不代表背后的模型足以理解任务。讨论能力时，应分别确认推理能力、可用操作、输入信息和执行环境。

| 对象 | 工作定义 | 应记录的身份 |
| --- | --- | --- |
| 模型 | 推理、生成与多模态计算组件 | 实际模型及配置版本 |
| Agent | 根据目标与反馈选择行动的执行逻辑 | 策略和提示版本 |
| 角色 | 任务中的责任 | 规划、执行、审核等 |
| 能力配置 | 模型、工具、知识、权限与环境组合 | 配置版本 |
| Worker | 承载执行的单元 | 实例 ID 与执行尝试 ID |
| 编排器 | 推进任务依赖、状态与恢复 | 工作流和任务版本 |

## 2. 为什么所有角色都可以视为 Worker

规划者的产物是计划，审核者的产物是验证报告，执行者的产物是代码。它们都接受输入、消耗预算并交付结果，因此可以共用创建、跟踪、取消和回收接口。

统一接口不代表职责相同。审核者通常应只读；执行者可以写入指定范围；规划者有权调整依赖，但不能因此自动取得所有业务系统权限。Worker 也可以运行确定性程序，例如格式校验器，无须每个环节都调用模型。

本仓库的 worker 狭义上指末端执行角色；本文的 Worker 是广义运行单元。secretary、planner、group 和 verifier 都可以由这种运行单元承载。

## 3. 工作流与自主 Agent 如何组合

当步骤、条件和检查可以明确表达时，优先用工作流约束过程；当下一步依赖语义判断和新证据时，可以在步骤内部使用 Agent。比如“测试失败后分析原因”需要判断，而“只有测试通过且审批有效才发布”适合明确规则。

自主程度越高，潜在行动空间越大，验证、预算和权限边界也应更明确。选型时先问“哪些决策确实无法提前写清”，再决定哪些节点需要自主性。

## 4. 四张图与系统边界

- 组织图：谁管理谁，谁有权裁决。
- 任务图：哪些任务依赖哪些结果。
- 通信图：谁向谁发送什么信息。
- 部署图：实例在哪里运行，使用哪些共享资源。

四张图不必相同。前端与后端可以属于不同组，在同一机器运行，并直接交换接口信息。把部署位置当成管理关系，会使迁移实例变成组织调整；把通信关系当成任务依赖，会无意中串行化本来可以并行的工作。

系统边界还应声明：管理的是研究过程、代码交付，还是生产发布？未被纳入边界的外部步骤，应保留为显式依赖，不能假定已经完成。

## 5. 练习与验收

以登录修复为例，列出目标、模型、客户端、工具、角色、实例、产物和外部系统；分别画出四张图。然后回答：更换模型、重启实例、增加审核者各改变了什么？如果无法分别回答，说明抽象还没有分开。
