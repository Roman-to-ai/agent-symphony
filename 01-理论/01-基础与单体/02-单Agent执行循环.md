# 02 · 单 Agent 执行循环

> 前置：01。目标：区分“持续运行”和“持续推进”，设计可停止、可检查的单体行为。

## 1. 执行循环的五个环节

Agent 每轮读取目标与当前事实，选择行动，执行工具，验证结果，再更新记录。执行失败也是新事实：权限拒绝说明当前路径不可行，测试失败说明候选结果尚未达到标准。忽略反馈而重复原操作，会把执行循环变成空转。

最低限度应记录：当前目标、最近行动、可观察结果、验证结论、剩余工作和下一步依据。不需要暴露模型内部思考过程，记录决策摘要和外部证据即可。

## 2. 长任务如何保持方向

把大目标分成可观察的里程碑。例如登录修复依次达到“可复现”“定位原因”“形成补丁”“回归通过”。每个阶段结束，写下已确认事实和未解决问题，再决定下一阶段。

计划是可修订的假设。遇到新证据后，应修改受影响部分并记录原因；不能为了服从旧计划继续已知无效的步骤。计划太细会在探索中迅速失效，太粗又无法验收，适宜粒度是能够独立检查的一段工作。

## 3. 无进展检测与停止策略

| 现象 | 判断依据 | 可选动作 |
| --- | --- | --- |
| 同一错误重复出现 | 参数、环境和错误实质未变化 | 停止盲重试，补充诊断 |
| 多轮没有新证据 | 产物、假设和验证结果无变化 | 换信息源或请求帮助 |
| 缺少权限或关键输入 | 当前 Worker 无法消除前置条件 | 进入阻塞并汇报 |
| 范围持续扩大 | 新工作超过任务契约 | 请求重新规划 |
| 达到验收要求 | 证据覆盖目标与约束 | 提交验收，停止探索 |

阈值应按任务设置，不存在普适的“连续三轮就失败”。工具调用时间长也未必没有进展，可以检查子进程状态、日志或阶段产物。

## 4. 单体能力边界与多体选择

单体常见瓶颈包括上下文负担、注意力分散、串行耗时和自评偏差。更大的上下文只能缓解部分信息容量问题，不能自动消除串行依赖或职责冲突。

在短任务、共享状态高度耦合、拆分成本高或验证方法清晰时，单体可能更合适。引入其他 Agent 应针对明确瓶颈，例如独立收集资料或审核，而不是只因为“复杂”。文件数量只能作为本项目的判档提示，不能普遍预测难度。

## 5. 示例：修复循环

第一次运行测试复现失败后，保存输入与错误；第二步定位会话过期处理；第三步修改并测试。若错误不变，先确认测试实际执行的是新代码，再考虑假设是否错误。若第三方认证服务不可用，则标明外部阻塞，避免持续修改本地代码。

完成时交付补丁、复现测试、回归结果和未验证场景。尚未具备外部环境不能写成“全部通过”。

## 6. 练习与验收

为一个 Worker 写出阶段目标、进展信号、失败分类、求助条件、预算和停止条件。给它注入“工具永久拒绝访问”，检查它是否停止无效重试并明确指出阻塞来源。
