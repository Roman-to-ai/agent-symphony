# 04 · 目标、任务与验收契约

> 前置：01—03。目标：把需求变成能够委派、验证和恢复的工作单元。

## 1. 从愿望到可判定目标

“优化登录体验”没有明确完成条件。可以改写为“过期会话访问个人页时跳转登录，并在重新登录后返回原页面；已有有效会话行为保持正确”。目标描述可观察行为，方案描述实现方式，两者应区分，以免把某种实现误当成业务要求。

验收既包括功能，也包括范围和非功能约束。测试通过但修改了禁止访问的目录，仍然不满足契约；耗时达标但丢失数据，也不能交付。

## 2. 最小任务契约

| 字段 | 用途 | 登录任务示例 |
| --- | --- | --- |
| 任务身份与版本 | 对齐讨论对象，防止旧指令覆盖 | AUTH-07，版本 2 |
| 目标与背景 | 保留业务意图 | 过期后保留返回地址 |
| 输入和依赖 | 决定能否开始 | 接口约定、基线版本 |
| 交付物 | 明确结果位置 | 补丁、测试、验证报告 |
| 验收标准 | 定义通过与失败 | 过期、有效、非法地址三类场景 |
| 范围与权限 | 限制可修改对象 | 仅认证模块和对应测试 |
| 预算与截止 | 约束投入 | 到达预算前汇报未完成项 |
| 回报与取消 | 保证可管理 | 阻塞即报，取消后停止新写入 |

以上是设计建议，具体执行命令继续放在实操文档。

## 3. 接收确认与契约变化

接收者应确认目标、范围、依赖和预期开始时间。无法理解的边界应先澄清，不能靠猜测扩大权限。接收确认只证明任务被理解，不证明已开始，更不证明已完成。

需求变化时，记录新版本、变化原因、受影响任务和旧产物是否仍可用。旧验收结果要绑定旧输入版本；若接口改变，原来通过的测试未必继续有效。

任务取消也要定义结果：尚未开始则直接取消；执行中则停止新动作并记录已发生效果；外部动作无法撤销时，进入补偿或人工处理，不能只从任务列表删除。

## 4. 验收证据的层次

程序退出码可以证明某个检查过程完成，却不能独立证明检查充分。需要把每条标准与证据一一关联：输入是什么、执行了什么、实际结果是什么、对应哪版产物。

主观质量也可以建立可讨论的标准，例如报告是否覆盖指定问题、结论是否有来源、是否区分事实与推断。无法自动判断时，标记审核责任与判定方法，不强行用一个退出码代替。

## 5. 项目对应与练习

[任务模板](../../02-实操/skill-通用/reference/templates.md) 已覆盖目标、边界、验收与汇报。预算、任务版本和取消语义是可进一步补充的设计，不表示现有协议已自动执行这些字段。

**练习：**把“让网站快一点”改成可委派任务，写清基线、测试条件、目标、允许改动和结果位置。请另一位执行者只看契约，指出仍需猜测的地方。

**通过标准：**执行者知道做什么和何时停止，验收者能逐条判断，接手者知道产物对应哪个目标版本。
