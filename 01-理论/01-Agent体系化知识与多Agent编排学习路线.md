每章采用“核心问题—知识点—与你的理解的关系—学习验收”的结构。首次阅读先完成阶段一、二；阶段三用于建立可靠性基础；阶段四、五在已有最小系统后深入。

## 阶段一：基础概念与单体执行

### 01. 基本概念与系统边界

正文：[01-基本概念与系统边界](01-基础与单体/01-基本概念与系统边界.md)。

**前置知识：**无。

**核心问题：**Agent、Worker、模型、工作流和编排器分别是什么？

| 概念 | 本文中的工作定义 |
| --- | --- |
| 模型 | 提供语言、推理、视觉等能力的计算组件 |
| Agent | 根据目标、上下文与环境反馈，选择下一步行动的执行逻辑 |
| Worker | 承载任务执行的运行单元，可以运行 Agent，也可以运行确定性程序 |
| 角色 | 执行者承担的责任，例如规划、开发、审核 |
| 工作流 | 任务步骤、依赖和状态转换的描述 |
| 编排器 | 管理任务依赖、状态推进、执行协调与恢复的组件 |

这些术语在不同项目中可能有不同含义，阅读项目时应先映射其实际职责。

你的“所有 Agent 都是 Worker”的理解适合作为统一执行抽象。进一步要区分：角色是责任，能力配置是执行条件，实例是某次实际运行。一个角色可以由多个实例承担，同一实例也可能承担多个角色。

**学习验收：**能够画出一次用户请求经过模型、Agent、工具、运行环境和编排器的过程，并解释各自负责什么。

### 02. 单个 Agent 的执行循环

正文：[02-单Agent执行循环](01-基础与单体/02-单Agent执行循环.md)。

**前置知识：**01。

**核心问题：**一个 Agent 如何持续产生有效进展？

基本循环：观察 → 判断 → 行动 → 验证 → 更新状态。

- 观察：读取目标、任务状态、工具结果与环境变化。
- 判断：选择行动、修改计划、请求帮助或结束。
- 行动：调用工具、生成产物或委派子任务。
- 验证：检查行动是否成功、是否更接近目标。
- 更新：保存进度、错误、证据和下一步。

重点学习计划与行动的关系、工具失败处理、重复操作检测、无进展检测、求助条件和停止条件。

持续工作需要可验证的进展，不能用调用次数或在线时长代替。长任务应有阶段目标、预算边界和中断恢复点。

**学习验收：**能够解释 Agent 何时继续、何时换方法、何时求助、何时停止。

### 03. 模型、工具、Skill、MCP 与运行环境

正文：[03-模型工具Skill与运行环境](01-基础与单体/03-模型工具Skill与运行环境.md)。

**前置知识：**01—02。

**核心问题：**一个 Worker 的有效能力由什么决定？

Worker 的有效能力取决于执行逻辑、模型、上下文、知识、工具、Skill、权限、环境和预算的组合。这里是概念分解，不是可直接计算的加法公式。

| 组成 | 需要理解的问题 |
| --- | --- |
| 模型 | 推理、视觉、时延、价格、上下文容量是否适合任务？ |
| 工具 | 能执行什么动作？参数、错误、超时和结果如何处理？ |
| Skill | 有哪些可复用流程、经验与约束？ |
| MCP | 如何通过协议接入工具与资源？ |
| 知识与上下文 | 信息是否正确、足够、及时且与任务相关？ |
| 环境与权限 | 软件、文件、网络、凭证和授权是否齐备？ |

Skill 可以指导使用工具；MCP 提供接入机制；接入成功仍需正确调用和结果验证。图片理解还依赖模型能力、图片质量、输入方式和必要的图像处理工具。

**学习验收：**当 Worker 失败时，能区分是模型不足、工具缺失、信息不足、方法不当还是环境受限。

### 04. 目标、任务与验收契约

正文：[04-目标任务与验收契约](01-基础与单体/04-目标任务与验收契约.md)。

**前置知识：**01—03。

**核心问题：**怎样把模糊需求变成可以执行和验收的任务？

任务契约至少包含：

- 目标与业务背景。
- 范围、约束与禁止事项。
- 输入、依赖与可访问资源。
- 交付物、输出格式与验收标准。
- 预算、截止时间与权限。
- 汇报要求、异常处理与停止条件。

你的“下达比较简单”可以补充为：任务下达容易实现，但清晰的任务契约决定后续汇报、验收和恢复是否可行。

例如，“实现登录功能”需要继续明确认证方式、界面范围、接口、错误行为、测试要求与验收场景。

**学习验收：**另一个 Worker 无须反复猜测，就能依据任务说明执行；验收者能依据同一份说明判断完成程度。

## 阶段二：多 Agent 协作

### 05. 任务分解与依赖图

正文：[05-任务分解与依赖图](02-任务与协作/05-任务分解与依赖图.md)。

**前置知识：**04。

**核心问题：**什么时候拆分任务，哪些部分值得并行？

重点学习：任务粒度、依赖图、关键路径、条件分支、循环、资源冲突、计划修订与取消传播。

拆分需要权衡：独立性收益、交接开销、共享上下文成本和结果合并成本。存在循环的工作可以用状态机或包含循环的图描述，不应把所有任务都强行表示成 DAG。

可以并行的例子：相互独立的资料收集。需要协调的例子：多个 Worker 修改同一接口或同一文件。

**学习验收：**能把一个业务目标画成任务图，标出可并行部分、依赖和关键路径，并说明为何拆到这个粒度。

### 06. 组织结构、层级与能力匹配

正文：[06-组织结构层级与能力匹配](02-任务与协作/06-组织结构层级与能力匹配.md)。

**前置知识：**03—05。

**核心问题：**任务应该由什么团队承担？

需要分别设计四个变量：层级深度、管理跨度、执行并发和决策权限。

| 结构 | 常见适用条件 | 主要代价 |
| --- | --- | --- |
| 单中心 | 任务规模较小，需要统一决策 | 中心容易过载 |
| 层级 | 子任务能够按领域或阶段分组 | 传递延迟与摘要信息损失 |
| 流水线 | 阶段边界和输入输出清楚 | 阶段瓶颈、上游错误传播 |
| 共享任务池 | 任务相对独立，可由同类执行者领取 | 依赖、争抢和公平性管理 |
| 对等协作 | 需要跨专业持续交换信息 | 通信与决策协调成本 |

还需要学习能力注册、任务路由、模型选择、局部授权、升级求助和动态重组。

你的核心判断成立：合适的层级取决于业务。进一步要根据任务依赖、协调负载、信息损失和容错需求说明“合适”的依据。

务必分开四张图：组织图描述管理关系，任务图描述依赖，通信图描述信息交换，部署图描述运行位置。

**项目参照：**CrewAI 的层级流程由管理者委派任务、审核结果并判断完成情况。[Processes](https://docs.crewai.com/en/concepts/processes)

**学习验收：**能为同一个任务比较两种组织结构，说明预期收益与代价。

### 07. 通信协议与向上汇报

正文：[07-通信协议与向上汇报](02-任务与协作/07-通信协议与向上汇报.md)。

**前置知识：**04—06。

**核心问题：**如何交换信息，并让管理者及时采取行动？

消息类型包括任务下达、接收确认、健康、进展、阻塞、求助、结果、失败与取消。

| 汇报 | 应回答什么 | 不能据此推断什么 |
| --- | --- | --- |
| 健康 | 是否能够响应？ | 任务正在有效推进 |
| 进展 | 已完成什么，有何证据？ | 整体目标已完成 |
| 阻塞 | 原因是什么，需要谁提供什么？ | 多等一段时间就能恢复 |
| 结果 | 交付物在哪里，如何验证？ | 产物一定通过验收 |

建议理解结构化消息字段：任务 ID、消息 ID、执行尝试 ID、发送者、消息类型、状态版本、证据引用与所需动作。

研究定期汇报、里程碑汇报、异常触发和主动查询的组合；同时处理消息重复、乱序、过期、丢失与消费失败。摘要应能追溯原始证据。

**项目参照：**AutoGen Core 提供基于 Actor 思路的 Agent 和异步消息机制，适合学习事件驱动协作。[Core](https://microsoft.github.io/autogen/dev/user-guide/core-user-guide/index.html)

**学习验收：**管理者可以依据汇报决定继续等待、补充信息、重新规划或替换 Worker。

### 08. 协作策略与集体决策

正文：[08-协作策略与集体决策](02-任务与协作/08-协作策略与集体决策.md)。

**前置知识：**05—07。

**核心问题：**何时分工，何时独立思考，何时互相审核？

学习分工执行、并行独立求解、交叉审核、辩论、投票、专家路由和多方案探索。

比较时关注信息独立性、证据质量、协调成本与裁决方式。多个 Agent 可能因使用相同模型、资料或提示而产生相关错误；多数同意不能代替事实验证。

**项目参照：**Anthropic 的研究系统展示主 Agent 委派和并行研究，也讨论委派、评估及协作成本。[工程案例](https://www.anthropic.com/engineering/multi-agent-research-system)

**学习验收：**能够说明一种协作策略为何适合当前任务，以及如何判断协作收益。

## 阶段三：状态与可靠运行

### 09. 状态、上下文、记忆与产物

正文：[09-状态上下文记忆与产物](03-状态与可靠性/09-状态上下文记忆与产物.md)。

**前置知识：**04—07。

**核心问题：**换一个 Worker 后，任务还能继续吗？

| 对象 | 作用 | 示例 |
| --- | --- | --- |
| 状态 | 描述当前执行事实 | 任务阻塞、等待接口确认 |
| 上下文 | 支持当前决策的信息 | 目标、最近工具结果、相关资料 |
| 记忆 | 可跨阶段或跨任务复用的信息 | 用户偏好、验证过的经验 |
| 产物 | 执行产生的结果 | 代码、报告、数据、证据 |

学习状态机、权威状态源、版本控制、检查点、上下文选择与压缩、记忆检索和失效、产物追溯、并发更新和交接包。

关键状态不能仅保存在聊天中；持久化保存了什么、何时保存、是否真正落盘，都影响恢复能力。

**项目参照：**LangGraph 区分线程内检查点与跨线程 Store；内存中的检查点不能在进程重启后保留。[Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

**学习验收：**新 Worker 可以读取目标、已完成内容、产物、阻塞和下一步，继续执行任务。

### 10. 编排器、调度器与运行时

正文：[10-编排调度与运行时](03-状态与可靠性/10-编排调度与运行时.md)。

**前置知识：**05—09。

**核心问题：**哪些事交给 Agent 判断，哪些事由程序稳定执行？

| 职责 | 负责的问题 |
| --- | --- |
| 规划 | 接下来应该做什么，如何修改计划？ |
| 编排 | 依赖是否满足，任务状态如何推进？ |
| 调度 | 何时交给哪个执行者？ |
| 运行时 | 如何启动执行、传递消息、管理实例？ |
| 控制循环 | 实际状态偏离期望后如何纠正？ |

这些职责可以合并部署，但应保持概念清晰。复杂语义判断适合由 Agent 辅助；配额检查、状态合法性和超时处理通常适合明确规则。

学习控制平面与执行平面、事件驱动、状态机、控制循环和所有权边界。

**项目参照：**Kubernetes 控制器持续观察状态，使实际状态接近期望状态。[Controllers](https://kubernetes.io/docs/concepts/architecture/controller/)

**学习验收：**能定位“规划错误”“调度不当”“执行失败”和“状态推进错误”的区别。

### 11. 生命周期、故障检测与恢复

正文：[11-生命周期故障检测与恢复](03-状态与可靠性/11-生命周期故障检测与恢复.md)。

**前置知识：**07、09—10。

**核心问题：**Worker 或协调者失败后，如何安全继续？

生命周期包括创建、初始化、执行、阻塞、暂停、恢复、终止和回收。

故障需要区分进程退出、网络中断、工具错误、超时、语义错误和无有效进展。超时只能说明需要怀疑和处置，不能证明远端执行者已停止。

学习以下机制：

- 心跳与租约：发现失联并管理执行权。
- 检查点与执行历史：确定恢复位置。
- 重试、退避、上限与熔断：避免持续放大失败。
- 幂等与去重：防止重复操作造成重复业务效果。
- 补偿：处理已经产生但需要撤销或修正的效果。
- 执行代次与提交校验：阻止旧 Worker 恢复后覆盖新结果。
- 协调者接管与持久状态：避免管理节点成为不可恢复的单点。

典型恢复过程：检测异常 → 标记执行尝试失效 → 收回或隔离旧执行权 → 加载状态 → 选择恢复策略 → 新实例继续 → 验证产物。

提交校验必须由实际写入方或接收方执行；只在消息中附带代次，不能阻止外部系统接受旧操作。重复投递也不等于业务效果能被重复执行，外部副作用需要单独设计。

**项目参照：**Kubernetes Lease 可用于心跳和领导者协调；Temporal 工作流提供持久化执行与恢复机制。它们分别帮助理解存活管理与任务继续执行。[Leases](https://kubernetes.io/docs/concepts/architecture/leases/)、[Temporal Workflows](https://docs.temporal.io/workflows)

**学习验收：**能说明任一步骤中断后从何处继续，以及哪些操作可能重复、如何限制重复副作用。

### 12. 结果合并与端到端验收

正文：[12-结果合并与端到端验收](03-状态与可靠性/12-结果合并与端到端验收.md)。

**前置知识：**04—11。

**核心问题：**所有 Worker 都提交后，如何确定整体任务完成？

区分三个状态：Worker 声称完成、子任务通过验收、整体目标通过验收。

学习格式与约束校验、事实和证据检查、独立审核、测试、产物合并、冲突裁决、接口兼容和返工范围。

系统状态可以包含：等待 → 就绪 → 执行 → 待验收 → 成功；验收失败可以进入返工、失败或重新规划，而不是直接把“提交”当作“成功”。

**学习验收：**能够用证据说明目标已实现，并在失败时定位需要返工的任务。

## 阶段四：资源与治理

### 13. 资源分配、预算与弹性调度

正文：[13-资源预算与弹性调度](04-资源与治理/13-资源预算与弹性调度.md)。

**前置知识：**05、10—12。

**核心问题：**有限资源下，怎样得到更高的有效产出？

资源包括费用、Token、模型请求配额、并发连接、CPU、内存、GPU、上下文容量和截止时间。

学习优先级、关键路径调度、预算分层、队列、限流、背压、公平性、资源预留、抢占、降级和扩缩容稳定性。

增加 Worker 前应判断：是否存在独立就绪任务，是否有配额与预算，是否受下游瓶颈限制，以及新增收益是否覆盖协调成本。

你的 Kubernetes 类比可保留，但要区分：运行实例健康、任务持续推进、业务结果正确。自动拉起实例只覆盖其中一部分。

**项目参照：**Kubernetes 支持根据观测指标调整工作负载规模；Agent 系统需要另外设计任务和预算指标。[Autoscaling](https://kubernetes.io/docs/concepts/workloads/autoscaling/)

**学习验收：**能够解释预算减半或任务量增加时的调度、降级和扩缩容策略。

### 14. 权限、隔离与信任边界

正文：[14-权限隔离与信任边界](04-资源与治理/14-权限隔离与信任边界.md)。

**前置知识：**03、07、10。

**核心问题：**一个执行者犯错时，影响能否被限制？

学习最小权限、任务授权、委派边界、凭证管理、文件和网络隔离、外部输入可信度、提示注入、工具结果验证和审计。

应区分读取到的信息、他人提出的指令和系统真正授予的权限。子任务所需权限可以小于父任务权限。

**学习验收：**能说明每个 Worker 能读什么、改什么、调用什么，以及授权如何收回。

### 15. 人工介入与可控自主

正文：[15-人工介入与可控自主](04-资源与治理/15-人工介入与可控自主.md)。

**前置知识：**09—14。

**核心问题：**人如何参与关键判断并保持任务可恢复？

学习介入触发条件、待审批状态、决策上下文、目标修改、预算调整、暂停、取消、接管和恢复。

人工等待应成为可持久化状态；进程重启后仍应知道在等待谁、批准什么以及批准是否仍适用于当前版本。

**学习验收：**系统可以在等待期间中断，再恢复原有等待或执行有效的人类决策。

## 阶段五：评估与持续演进

### 16. 可观测性、实验与评估

正文：[16-可观测性实验与评估](05-评估与演进/16-可观测性实验与评估.md)。

**前置知识：**完成阶段一至三；基础日志和证据记录应从首次实践开始。

**核心问题：**如何证明编排策略有效？

建立追踪链：目标 → 任务 → 执行尝试 → Worker → 模型与工具调用 → 产物 → 验收。

指标包括任务成功率、质量、时延、成本、人工介入率、返工率、重复劳动、通信开销、等待时间和故障恢复时间。

实验应比较相近预算与验收要求下的单 Agent、多 Agent、不同层级、模型组合和协作策略。记录多次运行的差异，避免用单个成功案例证明普遍收益。

故障实验可以覆盖 Worker 崩溃、网络延迟、重复消息、工具失败、预算耗尽和协调者重启。

**学习验收：**能用数据说明一个设计改动改善了什么、增加了什么成本，以及结论适用于哪些任务。

### 17. 经验沉淀与系统演进

正文：[17-经验沉淀与系统演进](05-评估与演进/17-经验沉淀与系统演进.md)。

**前置知识：**09、12、16。

**核心问题：**怎样积累经验而不积累错误？

学习失败分类、有效经验提炼、Skill 更新、提示词版本、模型路由调整、组织策略优化、回归评估和回滚。

区分单次任务经验、跨任务可复用经验和平台级规则。经验需要保留来源、适用条件与验证结果。

建议顺序：人工总结 → 验证有效 → 版本化发布 → 小范围观察 → 扩大使用。更自主的策略更新需要对应的评估和恢复能力。

**学习验收：**能解释为何写入某条经验、如何验证，以及效果变差时怎样撤回。

### 18. 支撑理论与进一步研究

正文：[18-理论基础与研究方向](05-评估与演进/18-理论基础与研究方向.md)。

**前置知识：**先有具体问题，再按需深入理论。

| 建议顺序 | 理论 | 对应问题 |
| --- | --- | --- |
| 1 | 图论与调度基础 | 任务依赖、并行性、关键路径 |
| 2 | 状态机与分布式系统 | 状态推进、消息、故障、幂等与一致性 |
| 3 | 排队论 | 队列积压、等待时间、瓶颈与并发 |
| 4 | 控制理论 | 反馈、自动纠偏、扩缩容与振荡 |
| 5 | 运筹优化 | 预算约束下的任务与模型分配 |
| 6 | 组织设计与团队决策 | 管理跨度、授权和协调成本 |
| 7 | 决策理论与信息价值 | 是否继续搜索、验证、委派或停止 |

进一步可以研究动态组织、异构模型协作、部分可观测决策、多目标优化和在线策略学习。这些适合作为进阶方向，不必成为搭建最小系统的前置条件。

**学习验收：**能够把实际问题映射到理论模型，并说明模型假设和现实的差异。

## 贯穿学习的实践任务

建议固定一个小任务逐步扩展，例如“实现一个包含前端、后端和测试的小功能”。保持任务不变，可以更清楚地比较每次增加机制带来的收益与成本。

| 步骤 | 实践内容 | 验收重点 |
| --- | --- | --- |
| 1 | 一个 Worker 完成任务 | 有目标、产物、验证与停止条件 |
| 2 | 拆出前端、后端和测试 | 明确接口、依赖和任务边界 |
| 3 | 加入协调者和任务契约 | 委派清楚，职责可追溯 |
| 4 | 加入进展、阻塞和结果汇报 | 管理者能够据此采取行动 |
| 5 | 保存状态、产物与交接信息 | 新 Worker 能够接手 |
| 6 | 中途终止 Worker 并恢复 | 不丢进度，不接受过期提交 |
| 7 | 加入集成验收和返工 | 子任务成功后仍验证整体目标 |
| 8 | 限制预算和并发 | 资源受限时按规则运行 |
| 9 | 增加权限和人工介入 | 可暂停、授权、接管和恢复 |
| 10 | 与单 Agent 基线比较 | 评估质量、时间、成本与协调开销 |

每一步记录：问题、当前设计、采用机制、预期收益、验证结果和剩余限制。

## 你的原始理解如何扩展

| 原始主线 | 扩展后的范围 | 优先章节 |
| --- | --- | --- |
| 合适的层级最好 | 任务依赖、层级、跨度、并发、授权和四张图 | 05—06 |
